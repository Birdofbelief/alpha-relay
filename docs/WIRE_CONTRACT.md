# 线格式契约

**这份文档描述的是「字节长什么样」，不是「代码怎么写的」。**

它存在的唯一理由：让消费端（券商执行端、监控脚本、告警机器人）在框架内部重构时
**一行都不用改**。所以这里的每一条都是被 `tests/golden/*.json` 与
`tests/test_wire_contract.py` 冻结住的 —— 改动它们中的任何一条，测试会红。

---

## 一、四个 channel

| channel | 文件名 | **谁写** | 读的人 |
|---|---|---|---|
| `signals` | `trade_signals.json` | 产生端 | 执行端 |
| `heartbeat` | `heartbeat.json` | 产生端 | 监控 |
| `positions` | `positions.json` | **执行端** | 产生端 |
| `executions` | `executions.json` | **执行端** | 产生端 |

**「谁写」是硬约束，且写在代码里**（`transport/base.py` 的 `CHANNEL_OWNERS`）。
`SingleWriterGuard` 会在运行期拒绝越权写入并抛异常 —— 不是打警告。

> ★ 为什么这条是硬约束而不是风格偏好：Gist 的更新是 **read-modify-write，非原子**。
> 两个写者同时改同一个文件，后写的会静默覆盖先写的。「静默」是关键 ——
> 两边都以为自己写成功了。

## 二、`signals`

```json
[
  {
    "id": "20260918144500_510050.XSHG_buy",
    "code": "510050.XSHG",
    "action": "buy",
    "amount": 1000,
    "price": 1.2346,
    "time": "2026-09-18 14:45:00",
    "signal_type": "demo_entry",
    "processed": false
  }
]
```

| 字段 | 说明 |
|---|---|
| `id` | **幂等键。** 构成 = `strftime("%Y%m%d%H%M%S") + "_" + code + "_" + action` |
| `code` | **JQ 形式后缀**（`.XSHG`/`.XSHE`），见第四节 |
| `action` | 只有 `buy` / `sell` |
| `amount` | 股数。**卖出为 0** 表示「全部卖出」 |
| `price` | 4 位小数。0 表示「无有效价」（停牌） |
| `time` | `str(datetime)`，见第三节 |
| `signal_type` | 自由文本，供策略标注来源（会进日志） |
| `processed` | **已废弃**，恒为 `false`。见第六节 |

### ★ `id` 的唯一性有前提，不是保证

产生端**不去重**。所以 `id` 唯一的前提是：

> 同一秒内、同一代码、同一方向，只推一次。

这个前提在单进程单线程下成立。**它不是一个全局唯一性保证** —— 若将来引入
多进程并发产生信号，必须自己补去重，否则两笔不同的单会共用一个幂等键，
而执行端会认为第二笔是重复的。

## 三、时间格式：**同一份契约里有两种，这是刻意的**

| 字段 | 格式 | 由谁解析 |
|---|---|---|
| `signals[].time` | `str(datetime)` → 可能带微秒 | **没有任何硬解析器** |
| `executions[].time` | `str(datetime)` → 可能带微秒 | **没有任何硬解析器** |
| `positions.update_time` | `str(datetime)` | 只做 `[:10]` 取日期 |
| **`heartbeat.last_time`** | **`strftime("%Y-%m-%d %H:%M:%S")` → 不带微秒** | **`strptime('%Y-%m-%d %H:%M:%S')` —— 全系统唯一的硬解析器** |

### ★★ 这个坑的完整失效链（真踩过）

消费端监控脚本里有这样一段：

```python
datetime.strptime(last_time, '%Y-%m-%d %H:%M:%S')   # ← 唯一的硬解析器
```

它被一个**裸 `except Exception`** 包着，解析失败时静默返回 `None`；
而 `None` 在上一层的语义是「没有历史时间戳可比」，于是**滞后检测直接跳过**。

所以：`heartbeat.last_time` 一旦带上微秒（`…14:45:00.878982`），

```
带微秒 → strptime 抛 ValueError → 被 except 吞掉 → last_dt = None
      → 滞后检测跳过 → 心跳停了也不告警 → **静默失效**
```

**没有任何一层会报错。** 这就是为什么 `heartbeat.last_time` 必须用
`strftime` 而不是 `str(datetime)`。

> ★ **`tests/golden/heartbeat.json` 自己抓不到这个 bug。** 固定时钟的微秒位是 0，
> 所以两种写法在 golden 里**逐字节相同**。要抓它必须用带微秒的输入 ——
> `tests/test_wire_contract.py::test_the_heartbeat_trap_is_real_not_imagined`
> 就是干这个的：它先证明「朴素写法确实会让 `strptime` 抛异常」，
> 再断言线格式不是那种写法。

### 读入侧必须宽容

`heartbeat` 的**读取**要能容忍历史遗留的带微秒值（把毫秒部分切掉即可）——
存量数据里可能有。宽容只在读入侧，写出侧必须严格。

## 四、后缀：**两套并存，不要「顺手统一」**

| 出现位置 | 后缀 | 例子 |
|---|---|---|
| `signals[].code`、`signals[].id` | JQ 形式 | `510050.XSHG` / `159919.XSHE` |
| `executions[].code` | JQ 形式 | `510050.XSHG` |
| **`positions.positions` 的键** | **PT 形式** | `510050.SS` / `159919.SZ` |

**原因**：`positions` 的键是执行端**直接从券商 SDK 的持仓字典里原样取出来写的**，
那是券商自己的写法。产生端读回来时转换即可，但**写出去的那份字节必须是券商形式** ——
因为它是给券商端的人看的，也是跨版本兼容的锚点。

> ★ 这一条曾经在本框架里被写错：`positions` 的键写成了 `.XSHG/.XSHE`，
> 而**所有测试都是绿的** —— 因为测试是手写 key 传进去的，绕过了写入边界。
> 「测试里的格式」和「真落盘的格式」不是同一个东西，这是那一课的准确表述。
> 所以 `tests/test_end_to_end.py` 现在直接读**磁盘上的字节**来断言，
> 不复用任何解析器。

后缀规则本身：**只看首位数字** —— `5`/`6`/`9` 归上交所，其余归深交所。

## 五、`executions`：**两种互斥的形态**

同一个数组里，非终态和终态的**字段集合不同**：

```json
// 非终态：submitted / skipped / failed
{
  "signal_id": "...", "code": "510050.XSHG", "action": "buy",
  "status": "submitted",
  "reason": "市价低于限价，挂单等待",
  "time": "2026-09-18 14:45:00"
}

// 终态：filled / canceled
{
  "signal_id": "...", "code": "510050.XSHG", "action": "buy",
  "status": "filled",
  "order_id": "PAPER-1",
  "price": 1.2346,
  "amount": 1000,
  "time": "2026-09-18 14:45:00"
}
```

- **终态只有 `filled` 和 `canceled`。** 只有终态才允许把对应信号从队列里清掉。
- **`submitted` 显式不删。** 它的语义是「已下单、结果未知」——
  删了就等于「单子还挂着、你却忘了它」。次日重试靠它。
- `limit_price` **不是本契约的字段**（它曾经在某个版本的源码注释里出现过，
  但不存在于任何实际写出的记录中）。

> ★ 形态混淆是静默的：读 `terminal` 记录时若按非终态去取 `reason`，
> 你得到的是 `None` 而不是报错；反过来读 `submitted` 的 `price`，
> 会拿到一个不存在的价格并当成 0。两种都不会抛异常。

## 六、`positions`：**三种输入形态，一个输出形态**

**写出**永远是包装形态（`tests/golden/positions.json`）：

```json
{
  "update_time": "2026-09-18 14:45:00",
  "total_value": 12345.6,
  "cash": 2345.6,
  "positions": {
    "510050.SS": { "amount": 1000, "cost": 1.2346 }
  }
}
```

**读入**必须同时认三种（存量数据里三种都有）：

| 形态 | 长相 | 后果 |
|---|---|---|
| A 包装 | `{"positions": {...}, "cash": …, …}` | 正常 |
| B 裸 dict | `{"510050.SS": {...}, ...}` | 能用，但 `update_time` 恒空 → 买入日期退化为今天 |
| C 旧 list | `[{"code": ..., "amount": ...}, ...]` | 同上 |

### ★ 认不出的形态必须**抛异常**，不能返回空快照

这是整套风控的支点，方向不能反：

```
读不懂持仓 → 若当成「确认空仓」 → 放心买入 → 而账户里其实还持有别的标的
           → 双持仓（真金白银的错）
读不懂持仓 → 抛 WireFormatError → 存储层转 None（= 未知）→ 闸门禁买、卖出照常
```

第二行才是对的。**「读不懂」和「确认空仓」是两件事，合并它们会开错仓。**

> ★ 本框架初版在这里 fail-open：非 dict 输入返回空快照。当时的测试甚至
> **断言了这个行为**（「非 dict 输入返回空快照，不抛异常」）—— 断言写反了，
> 测试就会一直替 bug 背书。这也是为什么「测试全绿」不能替代
> 「测试断言的是对的事」。

## 七、兼容性检查清单（改动前逐条过）

要动线格式时：

1. 改 `tests/golden/*.json` 了吗？—— **没改就是没改格式**，别只改代码。
2. 新增字段可以，**改名字/改类型/删字段不行** —— 消费端在别的进程里，独立升级。
3. 读写往返**不得丢掉本端不认识的字段**。执行端某天给信号加一个字段，
   产生端若「读进 dataclass → 写回去」，那个字段就被静默抹掉了，
   而症状是间歇性的（只在恰好那一刻读写时发生）。
   本框架所有 read-modify-write 都在**原始 dict** 上做增删。
4. 后缀、时间格式、终态集合 —— 这三样**都要单独想一遍**，
   它们各自都有「看起来该统一、实际不能统一」的理由。
