# 脱敏

本仓库的硬性要求是**零凭据字面量**，并且这不是靠人工检查维持的 ——
`tools/sanitize_check.py` 是**门禁**，装成 git pre-commit 钩子，命中即拒绝提交。

> ★ **克隆之后要手动开一次这个钩子** —— `core.hooksPath` 是**本机配置，
> 不随克隆带走**：
>
> ```bash
> git config core.hooksPath .githooks
> git config --get core.hooksPath      # 应输出 .githooks；空 = 没开
> ```
>
> 没开的话扫描器**一次都不会跑**，而**每次提交看起来都完全正常**。
> 这就是本仓库反复在防的那种假绿灯：唯一能发现泄漏的时刻静默地过去了，
> 终端上没有任何东西提示你。

## 一、什么不该进这个仓库

| 类别 | 具体 | 为什么 |
|---|---|---|
| **凭据** | `GIST_ID` / `GITHUB_TOKEN` / `SERVERCHAN_SENDKEY`、任何 `ghp_` / `github_pat_` / `SCT…` 字面量 | 一旦进 git 历史，删掉文件也没用 |
| **策略** | 核心因子公式与其结构、**标的池的具体代码**、全部阈值常量、分级阈值表、止盈止损规则 | 这些合起来就是 alpha 本身 |
| **实盘痕迹** | 策略日志、历史缓存、状态文件、真实 Gist ID、账户信息 | 泄露的是「在跑什么」 |
| **内部文档** | 运维备忘、开发日志、修复计划、轮换工单 | 含大量实盘阈值与事故细节，**整份不进** |

可复用的是它们**抽象后的工程结论**（失效方向、幂等、时间预算、网络韧性）——
这部分**重写**进 [`DESIGN_NOTES.md`](DESIGN_NOTES.md)，不搬运原文。

### ★★ 第一原则：**在结构上抠掉，不是用模式去拦**

上面那张表容易让人以为脱敏 = 攒一份关键词清单然后 `grep`。**这条路是走不通的**，
而且它的失败方式特别隐蔽。原因只有一句：

> **清单只认识「我提前想到的写法」，而泄漏出去的是「结构」。**

一个具体例子（本仓库真实发生过）：把策略从单文件脚本里搬出来时，我按关键词把
公式名、阈值、标的池都清掉了，清单一条没漏。**但漏了一个字段名** ——
策略原来读的那个私有辅助数据，接口在链路里留了下来，于是
`ctx.aux["<那个私有键名>"]` 这个**键名**、连同文档里的
`name = "<同一个键名>"` 示例，一起留在了公开 API 的 docstring 里。

它**不是任何一个关键词**，两条专门盯这块的正则**一条都没命中**。
可是它比阈值更值钱：**一个键名就把「我在算什么东西」说清楚了。**

所以顺序是：

| 顺序 | 做法 | 为什么是这个顺序 |
|---|---|---|
| **① 结构上抠掉（主力）** | 把原来放策略的地方**整个抠出来**，公开仓库只留一个**从零写的、最基础的**策略；`def`/签名/接口**照着私有那份抄**，**内容**一行不抄 | 抠掉之后，**那条路径根本不存在** —— 不存在的东西不需要被规则拦住 |
| **② 模式清单（绊线）** | 自备指纹清单（`tools/sanitize_check.py` 的第二类检查） | 它**兜不住**上面的例子。它的价值是「防止旧写法**回流**」，**不是**「证明干净」 |

**别把②当成交差的凭据。** 一份绿色的指纹清单能证明的只有一件事：
**你想到的那些写法没出现。** 它证不了「没有别的写法」。

推论：**别人给你一份「扫描通过」的报告时，问的是「你抠掉了什么」，不是「你扫了什么」。**

## 二、扫描器怎么用

```bash
python tools/sanitize_check.py            # 扫 git 已跟踪的文件（发布前跑这个）
python tools/sanitize_check.py --all      # 扫工作区全部文件（含未跟踪）
python tools/sanitize_check.py --staged   # 只扫暂存区（pre-commit 钩子用）
python tools/sanitize_check.py --path X   # 扫指定文件（可在仓库外，用于复核别人给的产物）
```

> **Windows 用户**：上面写的 `python` 是 macOS / Linux 上的通用写法；若你的
> `python` 指向微软商店的占位程序（执行无输出），把它换成 `py`。
> 见 README「快速上手」里那段说明。

退出码：`0` 干净 / `1` 有命中 / `2` **本次结果无效**（见第五节）。

它有一个刻意的设计：**只报「文件:行号:命中类别」，绝不打印命中的实际值。**
命中值一旦被打进 CI 日志或终端记录，脱敏本身就失败了 —— 报告把泄漏从
「文件里」搬到了「日志/终端/CI 输出」，而后者往往更容易被看到、被留存。

## 三、四类检查

| 类别 | 手段 | 清单谁提供 | 局限 |
|---|---|---|---|
| 凭据形状 | 正则（token 前缀、私钥块、32 位 hex…） | 代码内置 | 只认识**我提前想到的**形状 |
| **自定义指纹** | **正则**，一行一条 + 类别标签 | **使用者**（`.sanitize-markers.txt`） | 见第一节：**它拦不住它没想到的结构** |
| 内部文档 | **按文件名**拦，不读内容 | 代码内置 | 改名就绕过了 |
| **自备黑名单** | **字面量**匹配 | **使用者**（`.sanitize-deny.txt`） | 需要人维护 |

后两类**不能由扫描器猜**，必须由使用者提供。理由和第一节同一句：
像「我的标的池里具体是哪 21 个代码」这种事，扫描器不可能凭空知道 ——
可它恰恰是最该被检查的一类：**单独一个标的代码看起来完全无害，
几十个凑齐就是策略的核心资产。**

### 两份自备清单的区别（别搞混）

| | 黑名单 | 指纹清单 |
|---|---|---|
| 文件 | `.sanitize-deny.txt` | `.sanitize-markers.txt` |
| 写法 | 一行一条**字面量** | 一行一条**正则** + `TAB` + 类别标签 |
| 适合放 | 标的代码、Gist ID、账号名这类**精确字符串** | 「这类写法不该出现」：公式名、参数形状、命名习惯 |
| 命中时报告 | 命中类别 | **你自己写的标签**（所以标签要写得不含敏感信息，见下） |

> ★ **标签会出现在报告里，也会出现在测试里 —— 所以标签本身必须是无害的。**
> 报告只印「文件:行号:命中类别」，不印命中值；但「类别」这一栏是**你写的**。
> 把标签写成 `slope2_R2_三周期` 就等于**在报告里把指纹又讲了一遍** ——
> 脱敏把你泄露的东西从「文件里」搬到了「终端和 CI 日志」。
> 写成 `多周期结构` 这类**只描述形状、不含参数**的说法。
> （这条与第二节末尾「绝不打印命中的实际值」是同一条纪律，只是入口不同。）

## 四、★ 两份自备清单怎么建 / 怎么重建

两份清单都是**仓库根的文件**，都已被 `.gitignore` **按文件名精确挡住** ——
**这一点是关键：一个为了保密而存在的文件，绝不能自己成为泄漏源。**
（`.gitignore` 里那两条按文件名匹配，所以格式示例文件
`.sanitize-markers.example.txt` **照常入库**，不会被误伤。）

两份都可以用环境变量指向别处（换机器 / 放仓库外时用）：

| 清单 | 环境变量 | 默认路径 |
|---|---|---|
| 黑名单 | `SC_DENY_FILE` | `.sanitize-deny.txt` |
| 指纹清单 | `SC_MARKER_FILE` | `.sanitize-markers.txt` |

### 四之一、黑名单：一行一条字面量

### 首次建立 / 标的池变了之后重建

```bash
# 1) 从你自己的私有策略源里提取「不该出现在公开仓库」的字面量。
#    把 <私有策略源> 换成你本地的真实路径 —— 注意：**别把它写进任何入库的文件里**。
python - <<'PY'
import re, pathlib
src = pathlib.Path(r"<私有策略源>").read_text(encoding="utf-8")
# 例：抓标的池里的 6 位代码
codes = sorted(set(re.findall(r"\b[0-9]{6}\b", src)))
out = pathlib.Path(".sanitize-deny.txt")
out.write_text("# 由私有策略源生成，绝不入库\n" + "\n".join(codes) + "\n",
               encoding="utf-8")
print(f"写入 {len(codes)} 条 → {out}")
PY

# 2) 立刻验证它真的在工作（见下「验证黑名单不是摆设」）
python tools/sanitize_check.py --all
```

> ★ **不要用 `sed`/`awk` 之外的 shell 展开往这个文件写内容**。用哑引号 heredoc
> （`<<'EOF'`）或像上面这样交给 Python 写 —— 未加引号的 heredoc 会让 shell
> 先展开变量和正则元字符，把内容悄悄改掉，而**它不会报错**。

### 验证黑名单不是摆设

建完必须做一次**反向验证** —— 确认它真的能报出来：

```bash
# 临时指向一个含已知字符串的文件，确认命中（退出码应为 1）
python tools/sanitize_check.py --path <一个含该字符串的文件>; echo "退出码=$?"
```

**只测「干净输入 → 零命中」是不够的**：那既可能是「真的干净」，
也可能是「整条规则瞎了」。两者在终端上长得一模一样。

### 四之二、指纹清单：一行一条正则

格式见 **`.sanitize-markers.example.txt`**（**这份是要入库的**，它只讲格式、
不含任何真指纹）。结构是：

```
# 注释行：说明这份清单是「绊线」而不是「防线」
# expect: 3
ACME_INTERNAL_[A-Z]{2,}<TAB>内部标识
```

| 约定 | 说明 |
|---|---|
| 分隔符 | **一个真正的制表符 `TAB`**，不是空格 |
| 标签 | TAB **之后**是类别标签，会原样出现在报告里 → 见第三节的「标签必须无害」 |
| 省略标签 | 行尾就是 TAB（标签为空）→ 用默认标签 `自定义指纹` |
| `# expect: N` | 声明「这份清单应该有 N 条」。**对不上就整轮作废**（退出码 2） |
| 大小写 | 匹配时**忽略大小写** |

三种写法错误**一律硬失败**，绝不退化成「这条规则没命中」：

1. **一行里没有 TAB** —— 注意危险的是**空格**：`ACME_[A-Z]+ 内部标识` 会
   被当成**一整条正则**去编译。` 内部标识` 里的空格在正则里是合法的
   （匹配一个空格），于是它**编译得过、永远不会命中**。这是本节最阴的一种。
2. **正则编译不过**。
3. **`# expect: N` 与实际条数对不上**。

> ★ 为什么要 `# expect: N`：它是**防「静默变少」的绊线**。
> 清单是本机文件、不入库，所以**它少了一条没有任何人会知道**。
> 而这个数**必须写在私有清单里、不能写在公开测试里** ——
> 把 `assert len(labels) == 9` 写进公开测试，等于**在公开仓库里
> 把「该拦几类」说了出来**。绊线自己成了泄漏源。

### 四之三、两份都到齐才算「完整通过」

扫描器在**清单没加载到时刻意不打绿勾**，两份都缺时输出是：

```
⚠️ 脱敏扫描通过（**不完整**）：… 共 N 个，零命中，但 .sanitize-deny.txt 与
   .sanitize-markers.txt 未加载。
   未加载的那一类检查**没有执行** —— 要算完整通过，请在仓库根把这两份清单都建起来
```

两份都加载到才打印：

```
✅ 脱敏扫描通过：… 共 N 个，零命中（含自备黑名单 23 条、自定义指纹 10 条）。
```

**差别只在最后一行，而最后一行是唯一会被记住的那行。** 少了清单的「✅ 通过」
是一句会骗人的话：它看起来和完整通过一样，而恰恰是**对本仓库最要紧的那件事**没跑。
（`tests/test_sanitize_rules.py` 里有两条测试分别断言这两种措辞 ——
措辞退化在代码层面看不出任何区别，只在这一层拦得住。）

> ★ **CI 上跑出来的必然是「不完整」** —— 两份清单都被 `.gitignore` 挡住了，
> 公开克隆里根本不存在。所以 `.github/workflows/tests.yml` 里那一步
> 看到 `⚠️` **是正常的**，看到 `✅` 才该怀疑（说明有人把清单提交上去了）。
> **这是本仓库唯一一处「黄灯是对的」的地方** —— 写在这里以免下次有人
> 顺手把 CI 改成「必须绿」。真正的「完整通过」只能在你的本机跑。

## 五、★★ 一个只会静默失效的检查器有多危险

终端上「什么都没打印」和「检查通过了」**长得完全一样**。一个失效的门禁
不只是没起作用 —— 它会**冒充一个通过的门禁**，让人据此收工。

本扫描器在写出来的当天，**三条规则全是瞎的**。三次实录：

1. **`Finding = tuple`** 把 `Finding` 绑定到了内建 `tuple` 本身，
   于是 `Finding(a, b, c)` 变成 `tuple(a, b, c)` 并抛 `TypeError`。
   危险之处在于**字面量写法 `(a, b, c, "")` 全都正常**，只有唯一一处用
   `Finding(...)` 构造的地方会崩 —— 那是自备黑名单规则，**且它只在命中时才崩**。
   所以空跑、静态看，一切正常。这条规则从加上去到被发现，**一次都没成功报出过命中**。

2. **一条大正则把 Python 类型标注「顺手吃掉」**，于是 `gist_id: str,` 里的 `str`
   被当成凭据值 —— **每一处函数签名都成了命中**。误报的代价不是「吵」，
   是让人对整个检查失去信任、进而绕过它。

3. **默认模式依赖 `git ls-files`，而仓库没 `git init` 时它返回空表**，
   脚本于是报「✅ 共 0 个文件，零命中」—— 一个漂亮的假绿灯，
   亮在**「代码已经全写好了、检查一次都没跑过」**的那一刻。

三次的共同形状：**报「通过」的那条路是通的，报「命中」的那条路是断的。**
所以只测「干净输入 → 零命中」永远发现不了它们。

### 由此推出的三条规矩

1. **检查器的失效路径必须和它的通过路径长得不一样。** 所以脚本不写
   `sys.exit(main())`，而是把**自身崩溃**也渲染成一条明确输出并返回 `2`
   （`2` 的含义是「本次结果无效」，不是「有命中」）。
2. **每条规则都要有反向测试**（`tests/test_sanitize_rules.py`）：
   干净输入不报，**脏输入必须报**。
3. **本文件不能有 shebang 行。** 首行若是 `#!/usr/bin/env python`，
   Windows 的 `py` 启动器会去解析它，然后**零输出、退出码 49** 地直接死掉 ——
   不报错，什么都不说。文档里当时一律写 `py tools/sanitize_check.py`，
   也就是说**按文档调用它的每一次都会是零输出**。

### 2026-09-22 补：上面第 1 条在钩子里**复发了一次**，成因不同

同一句话（「钩子报「发现凭据」，但真相是检查根本没做」）以第二种方式出现过：
`.githooks/pre-commit` 当时把解释器写死成 `py`。在 PATH 里没有 `py` 的机器上
（= 所有 macOS / Linux），`py: command not found` 之后钩子**照样往下走**，
`$?` 拿到 127，于是把 127 当成「命中」并**指控提交者泄漏了凭据** ——
受害者会去查自己的 diff，而不是查钩子。

> 两种成因、一个症状：**失效路径长得和通过路径一样**。
> 所以钩子现在：① 从 `py` / `python3` / `python` 里**挑**一个，且不是只看
> 存在性 —— 要**试跑一次**（Windows 上 `python3` / `python` 常是微软商店的
> 占位程序：`command -v` 命中、一执行就退出码 49、零输出）。
> ② 三条失败路径各说各的话：「找不到解释器 ⇒ 这次检查**没做**」／
> 「扫描器退出码 2 ⇒ 本次结果**无效**」／「其余非零 ⇒ **命中**」。
> 三条都是 `exit 1`（fail-closed），但话不一样。

### 另有一条：构造 `Finding` 一律走 `Finding(...)`

不许写成字面量 `(path, i, cat, "")`。两者**相等**（NamedTuple 是 tuple 子类），
所以 `findings == []`、`len(...)`、`for a, b, c, _ in ...` 全都照常工作 ——
**唯独 `f.lineno` 会 `AttributeError`**，于是「类型标注写 `list[Finding]`、
实际给的是 tuple」这种谎言能一直不被发现。

## 六、误报怎么办：加精确豁免，不要关规则

确认是误报时，**加一条精确豁免**，不要整体关闭那条规则、也不要加
`--no-verify` 之类的绕过：

```python
# tools/sanitize_check.py
PLACEHOLDER_OK = re.compile(...)   # ← 允许的写法在这里集中列举
SELF_EXEMPT = {"tools/sanitize_check.py"}   # ← 自身豁免的**范围**要最小
```

> ★ **自身豁免的范围给宽一点，就是静默漏检。** 本文件初版对扫描器自身是整体
> `continue`，结果它自己注释里举的示例代码恰好是个真标的池成员，
> 而**唯一该发现它的检查正好被豁免掉了**。现在的实现是：豁免只覆盖那三类
> 内置规则，**两份自备清单照常执行**。
>
> ★★ 而这里还有一个**方向相反**的坑，两边都踩过才算懂：
> 指纹类**必须**对扫描器自己跑。因为**这个文件是公开的** ——
> 一条指纹若命中它自己的注释，那不是误报，**是真命中**。
> 而凭据类**必须**跳过它，因为扫描器**按定义**就要写出 `ghp_` 这种形状
> 的字面量来当正则。（初版把整条 `scan_text` 用在自身豁免上，
> 当场被凭据规则报出 `SECRETISH_NAMES` —— 它自己的一个大写常量名。）
> **「要不要豁免」不是按「是不是自己」定的，是按「这条规则命中自己时算不算真」定的。**

## 七、发布前的人工复核（扫描器只做一半）

扫描器是必要条件，不是充分条件。发布前还要做：

0. **★ 结构清扫（先做这个，它比后面三条加起来都值钱）。**
   把**公开 API 的每一个名字**拿出来，对着私有那份**逐个问「这个名字是不是
   从它那儿继承来的」** —— 不只是策略文件，**docstring、示例、参数名、
   辅助数据的键名、配置项的键名**，全都是泄漏面。
   做法：`grep -rn 'aux\[\|name\s*=\|参数名' signalchain/ docs/ tools/ tests/`，
   把命中的每一个标识符拿去和私有策略源**对一遍**。
   **别用关键词清单做这一步** —— 第一节那个例子正是清单一条都没命中的那个。
   判据：**「这个名字能不能让读者推断出我在算什么？」** 能，就换掉。
1. `git log -p --stat` 抽查**每一个 commit** —— 扫的是当前快照，
   而 git 历史里的东西删不掉。**改过旧提交之后要重跑这一步**：
   `filter-branch` 之类的重写会造出一批新 hash，**每一条都要重新看**。
2. 按第一节的表**逐项人工对照**一遍。
3. 确认 `python -m pytest` 全绿（测试里含「零凭据仍能跑通」的可执行证明）。
   **注意公开克隆里的条数会比本机少** —— 有几条测试带 `skipif`，
   条件正是「那份私有清单在不在」，它们在公开克隆里**必然跳过**。
   这不是测试被削弱，是**那几条本来就只对本机有意义**；
   但要**自己知道少了哪几条**，别把「294 passed, 2 skipped」读成「全跑过了」。
   （这个数会随代码变，别照抄 —— 以你自己那次实测为准。README「跑测试」
   一节记了它当初是怎么量出来的。）
4. 确认 `git status` 干净、没有意外的未跟踪文件（两份清单都必须在忽略列表里）。
