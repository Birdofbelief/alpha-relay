## 一、失效方向：判据是「哪边错了更疼」，不是「哪边更保守」

这是全库最重要的一条，也是最容易做错的一条。

### 主张

数据不全时，默认动作是「停」而不是「照做」。**但「停哪一半」必须按代价不对称来定。**

### 三个闸门，三个方向

| 闸门 | 触发 | 停什么 | 如果反过来做，会怎样 |
|---|---|---|---|
| `QuoteIntegrityGate` | 任一标的行情缺失 / NaN / 非正 | **全部停发** | 若「只停这一只」：其余标的的判断仍建立在坏数据上 —— 而**卖出同样是错的**，你可能卖掉一只本来健康的持仓 |
| `PositionsSyncedGate` | 未能与执行端完成对账 | **禁买，卖出照常** | 若「全停」：读不到持仓就不让卖，等于把**止损也一起停掉**，风险敞口留着 |
| `AuxDataGate` | 关键辅助数据整体缺失 | **禁开新仓，存量照管** | 若「全停」：辅助数据只用来挑新标的，缺了它不影响已有持仓的止盈止损 |

### ★ 反直觉的部分

**「一律全停」看着最安全，实际不是。** 它把三个代价完全不同的问题当成了同一个。

看第二行：持仓读不到时，买入的错是「可能重复建仓」（真金白银、不可逆），
卖出的错是「少卖一次」（下一轮还能卖）。**两个错差着量级，凭什么一起停？**
所以这里的方向是**禁买 + 放行卖出**，而不是「保守起见全停」。

第一行相反：行情坏了的时候，「只跳过坏的那只」看着更「精准」，
但坏行情污染的是**判断本身**，不是某一个标的。此时卖出也可能是在错价格上做的决定。

> **判据本身要写下来，否则它会被后人当成 bug 改掉。**
> 一个「禁买但允许卖」的闸门，在只读代码的人眼里非常像写反了 ——
> 所以 `gates.py` 里每个闸门的 docstring 都以「如果反过来会怎样」结尾。

### 代价

方向定错的代价，比「少做一次」大得多。这一条是从**实盘亏钱**里换来的，
不是从设计原则里推出来的。

## 二、幂等：靠「天然幂等」而不是靠去重

### 主张

信号带一个确定性 id，它就是幂等键：

```
id = strftime("%Y%m%d%H%M%S") + "_" + code + "_" + action
```

**同样的市场状态 → 同样的 id → 消费端能认出「这条我处理过了」。**

### ★ 这个唯一性有前提，而且前提不在本框架的控制内

产生端**不去重**。所以 id 唯一的前提是：

> 同一秒内、同一代码、同一方向，只推一次。

单进程单线程下成立。**它不是全局唯一性保证** —— 一旦引入多进程并发产生信号，
两笔不同的单会共用一个幂等键，而执行端会认为第二笔是重复的，**静默丢掉**。

减一层的措施：**时间戳取 `ctx.now` 而不是墙上时钟**。
这不只是为了可回放 —— 掺了墙上时钟，回放同一天的行情会生成一批全新 id，
「这条处理过没有」就永远答「没有」，幂等键直接失效。

### ★★ 重试时 id 必须不变：锚在**计划时刻**，不在实际时刻

上面那个 id 里的时间戳，取的是 `ctx.now` —— 也就是**这一轮实际跑到**的时刻。
一旦任务会重试，这里就有个陷阱：

```
计划 14:45，14:45:00 第一次跑 → id 尾号 144500
14:46:30 重试              → id 尾号 144630   ← 新 id！
```

执行端拿 `signal_id` 做幂等键，于是第二遍会被当成**一笔新单**。这不是理论风险：
修好「失败会重试」之后，重试从「极少发生」变成「默认路径」。

所以 `StrategyContext.signal()` 生成 id 时用的是：

- `anchor`（计划时刻，由调度器传入）—— 决定 `sig_id`
- `created_at` / 线上的 `time`（实际时刻）—— 记录「什么时候做的决定」

两者在正常时相等，只在迟到/重试时分叉。手工调用 `run_round()`（没有计划时刻）
时 `anchor` 为空，退回原来的行为。

> ★ 一般化的说法：**幂等键里的任何一维，只要它会在重试时变化，幂等就已经失效了**
> —— 哪怕变化的那一维看起来「更真实」。

这条**不依赖策略作者自觉**。`Signal` 是公开导出的，策略可以直接构造它，文档只是
「建议」走 `ctx.signal()`。所以调度器在信号发出前统一补锚：只要这条信号**没有显式给过
id**，就用本轮的计划时刻补锚并重算 `id`。

同理，派发任务时按**签名**判断要不要传计划时刻，而不是按对象身份
（`fn.__func__ is Runner.run_round`）—— 否则有人继承 `Runner` 重写 `run_round`，
`planned_at` 就悄悄传不进去，锚又退回实际时刻。**重写一个方法是正常的，不能因为它丢掉安全属性。**

### 为什么重试是安全的（这一条不显然）

`GistTransport._request` 重试时**原样重发同一份 body，循环内绝不重新 GET**。

这之所以安全，是因为本后端的写是**整体覆盖**语义 —— 重放同一份 body 天然幂等。
**如果写语义改成「追加」，这条重试立刻变成 bug**，会产生重复信号。
（所以 `_request` 的 docstring 里写明了这个前提。改写语义的人必须先看那句话。）

### 代价 / 已知缺口

- 同一秒内对同一代码发同方向的两笔**不同**订单 → 第二笔被当成重复。
  当前策略不会产生这种序列，但这是**约定**，不是**保证**。
- 真要修，得在产生端加一层去重；本框架刻意不做，因为那会引入新的共享状态。

## 三、时间预算：三个数，三种失败

无人值守的程序里，「错过」和「重复」是一对孪生事故。三个常量各治一个：

| 常量 | 值 | 治什么 |
|---|---|---|
| （匹配方式）`>=` 而非精确匹配 | —— | **错过**：30 秒一轮的循环，14:57:00 那一秒大概率不在循环里。精确匹配 = 当天不执行 |
| `catchup_minutes` | 30 | **迟到太久**：收盘后启动再补执行 14:57 的任务，等于拿早就作废的判断去下单 |
| `startup_min_budget_seconds` | 60 | **自己把窗口拖没**：启动时刷新历史缓存太久，会把下一个任务判成超时跳过 |
| `task_fail_limit` | 3 | **刷屏**：一个确定性异常每 30 秒抛一次，一天抛 2880 次，真告警被淹 |

### ★ 三个容易漏掉的细节

1. **跳过也要标记成「已执行」。** 否则每 30 秒重新判断一次，日志被同一句「已跳过」刷满。
2. **执行记录必须按天持久化 —— 这是正确性，不是优化。** 进程重启后忘了「今天跑过」，
   会**重新执行一遍**；在交易上，重复执行是真的会重复下单的。
3. **`>=` 把「错过」变成「延迟」，但延迟必须有上限。** 这两条是配套的，缺一条都不行：
   只有 `>=` 没有 `catchup_minutes` → 收盘后还在补单；
   只有 `catchup_minutes` 没有 `>=` → 晚 30 秒就整天不跑。

### ★★ 失败必须算失败：`RoundResult.error` 也是一种失败

调度器（`Runner.run_round`）**不会因为单轮异常杀进程**：它把异常记进
`RoundResult.error` 就返回。这是对的 —— 一个任务的失败不该带走其他任务。

但调度器（`run_due`）**必须认出这个返回值**。早先它只看「有没有抛异常」，
于是默认路径上：

- 任务天天失败，`executed_tasks` 照记 ⇒ **当天不再重试**
- 心跳照报 alive ⇒ 监控不会响
- 「连续失败上限」永远不触发 ⇒ 那三条日志永远不会出现

三条合起来：**进程活着、心跳正常、任务天天失败，而终端上没有任何痕迹。**
修法是：只要 `result.error` 非空，就按失败处理 —— 不记「已执行」、
失败计数 +1、心跳 escalate 到 error；到 `task_fail_limit` 才显式放弃当天。

★ 这条修复**必须和上一节的「锚在计划时刻」一起上**。失败会重试 ⇒ `decide`
会重跑 ⇒ 没有锚就会重复下单。两个补丁是配套的，不能只取一半。

### ★★ 一个已知的锋利边缘：连续失败上限的窗口只有 90 秒

`task_fail_limit = 3` × `LOOP_INTERVAL_SECONDS = 30` ⇒
**同一任务连续三次失败（约 90 秒内）就会放弃当天，心跳置 error。**

初衷是对的（不放弃 = 刷屏 2880 次），但这个窗口意味着：
**一次持续 90 秒的瞬时故障（网络抖动、数据源瞬时 5xx、一次重启）就能毁掉当天那个任务。**
上面那条修好之后，这个窗口才**真的生效** —— 以前它基本是块装饰。

这是**刻意保留**的行为，不是疏忽 —— 放弃是**显式**的（打日志 + 心跳置 error 等人工），
不是静默的。但用的人必须知道这个数。嫌短就调大 `SC_TASK_FAIL_LIMIT`：
把它乘以 30 秒，就是放弃前的总等待。

> ★ 由此推出一条更一般的教训：**「有 try 包着」不等于「安全」。**
> 主循环最外层那个 `except` 确实保证进程不死，但它同时把
> **「崩溃」变成了「放弃」** —— 而崩溃是响的，放弃是哑的。
> 排查时若只确认「进程还在跑」，就会漏掉这一类。

### 为什么带错误活着

主循环最外层捕获一切并继续。对比：
- **崩掉** → 当天所有剩余任务都不执行，而且**没有心跳了**，监控端什么都看不见
- **继续** → 至少心跳还在，人能看见，来得及介入

孤独运行的程序，**带着错误活着**远比干脆死去有价值。
唯一例外：`OwnershipError`（写错 channel）**必须让它响** —— 那是编程错误，
吞掉它等于把架构违规藏起来。

## 四、网络韧性：区分「值得重试」和「重试只会更糟」

### 主张

重试不是「多试几次」。**先分类，再退避，最后才是次数。**

```python
RETRY_STATUS = frozenset({429, 500, 502, 503, 504})
```

**401 / 403 / 404 刻意不在其中。** 它们的意思是「token 失效」「gist 被删」「ID 写错」——
是**配置错了**，不是瞬时故障。重试只会：
1. 把配额耗光（Gist 带 token 才 5000 次/小时）
2. **推迟你发现配置错误的时间** —— 而这类错误最贵的地方就是发现得晚

### 四条具体做法

| 做法 | 理由 |
|---|---|
| **超时必须有值**（默认 15s） | 一个**卡住**的请求比一个**失败**的请求更难排查，而且会直接吃掉交易窗口的时间预算 |
| **指数退避 + 随机抖动**（`1.5·2^n + U(0,0.5)`） | 抖动是为了错峰 —— 没有它，多个进程会同时重试、同时失败 |
| **`Retry-After` 优先** | 429 时服务端明确告诉你等多久；自己猜的退避序列只会更糟 |
| **重试耗尽返回最后一次响应** | 让调用方走它自己的降级分支，而不是在本层抛一个它无法处置的异常 |

### 读操作刻意不缓存

`GistTransport.read()` 每次都发真实 HTTP 请求，**不做整份 gist 的缓存或复用**。

这不是没做优化，是**拒绝**了一个优化：缓存会让「读到的」和「实际存的」出现时间差，
而在交易链路上，这个时间差的表现形式是**「用旧持仓做了新决策」** ——
属于最贵的一类错误。配额换正确性，这里划算。

### 配额纪律

Gist 匿名 60 次/小时、带 token 5000 次/小时。所以后端**每次只读写需要的那一个文件**，
绝不整份拉取 —— PATCH body 里只放这一个文件，gist API 只替换显式给出的文件。

### 日志里绝不放凭据

`describe()` 返回 `gist:<sha256(id)[:8]>` ——
**可区分身份、但不可用于访问**。gist_id 和 token 一个字都不进日志。

> secret gist **不是 private**，它是「不被检索到」，不是「访问不了」——
> 知道 ID 的人就能读。所以 Gist ID 本身按凭据对待。

### ★ 第三方库内部的裸请求：超时不在我们手里

上表那句「超时必须有值」只约束**本仓库自己发的**请求。真正难查的坑在别人的代码里：
`akshare` 的 `tool_trade_date_hist_sina()` 内部自己发 HTTP，**不传 timeout**；
而 requests 在没有 timeout 时**没有默认上限**。

后果不是崩溃，是**主循环冻结**：进程活着、心跳照写、当天所有定时任务一个都不执行，
日志停在最后一行。这种形状会让人去怀疑策略和券商，而不是怀疑日历。

两条结论：

1. **`socket.setdefaulttimeout()` 对 requests 无效。** 它只对「参数完全省略」生效，
   而 requests 会把这个值显式塞进自己的调用参数里，把默认值盖掉 ——
   一个看起来完全正确的药方，实测无效。
2. **正确的位置是我们自己这一层。** 给 loader 套有界调用（`calendar.py` 的 `_bounded_load`）：
   到点放弃 → 保留旧缓存 → 告警 → 主循环继续。并且**同一时刻只允许一个加载在飞**，
   否则每个刷新周期再挂一个线程，「卡住」会升级成「卡住 + 泄漏」。

残余风险如实记：这套超时只覆盖「等多久」，**不覆盖 DNS 解析**（`getaddrinfo` 无上限）。

### 跨源替补：只有「整表换源」这一种做法

实时行情目前是单源 + 同源重试（`RetryingMarketData`）。如果要加第二家行情商，
下面五条是**约束**，不是建议 —— 每一条都对应一次真实事故：

| 约束 | 为什么 |
|---|---|
| **只许整表换源，不许逐只混源** | 逐只混会让两家的价在**同一次比较**里并存 ⇒ 静默改变「该买哪只」，事后无法从日志复现 |
| **备源要独立请求，不复用其它用途的同一个源** | 复用会把两件事的失败语义绑在一起；两者不同频 ⇒ 用到的是「那一刻」的价，越往后越旧 |
| **替补路径必须有测试真的走到** | 「永远走不到」的分支不报错，只是永远 fail-closed —— 这就是 `RetryingMarketData` 补测试的理由 |
| **替补失败仍然 fail-closed，不许拿缓存或过期快照顶** | 与 §五 同源：坏数据比没有数据危险 |
| **要有「一键回滚」开关** | 参数与口径是实测出来的，不是文档给的；口径没验完之前必须能一键退回单源 |

**外加一条反向结论：历史日线不该加替补。**
复权只调历史、不调当日；两家源的复权口径拼在一起，会造出**凭空的趋势破位** ——
与 §五「不同源的历史不可拼接」是同一个原因。

## 五、行情缓存：宁可不可用，不可用错的

行情层的每一个检查都遵循同一条：**坏数据比没有数据危险。**

| 检查 | 动作 | 为什么不能放行 |
|---|---|---|
| 复权异常跳变（`detect_adjustment_jump`） | **不缓存、不返回** | 一份未复权的序列会造出**凭空的趋势破位** |
| 复权口径变了（缓存 `qfq` → 现在 `hfq`） | **整份丢弃** | 绝不拼接口径不同的两段序列 —— 接缝处会造出一个假跳空 |
| 缓存落后 > `max_stale_days`（默认 1） | **跳过该标的** | 用的是「旧价」下的判断 |
| 缓存落后 == `STALE_WARN`（1 个交易日） | 用，但计数 | 落后一天通常可接受，但**必须留下痕迹**（`stale_used` 计数会进日志） |

`describe()` 把命中/留存/跳过三个计数暴露出来，就是为了让「今天有多少判断是用旧数据做的」
可查 —— **一个不可观测的降级等于没有降级。**

### 涨跌停：交易所规则属于链路层，不属于策略

「该买哪只」是策略的事；「这个价格买不买得到」不是。涨跌停属于后者：

| 现象 | 纸面端该怎么做 | 为什么 |
|---|---|---|
| 现价 ≥ 涨停价，想买 | `submitted`（挂单等待） | 板上的卖单轮不到你，判成交等于白送一个买点 |
| 现价 ≤ 跌停价，想卖 | `submitted` | 同上，反方向 |
| 前收盘价拿不到 / 为 0 | **不判**（退回原行为） | 不知道 ≠ 没有涨跌停；把「不知道」当成 0 会拦住一切交易 |

`submitted` 是刻意的第三态：它既不是成交也不是失败，和「停牌挂单等待」同一语义。
判 `failed` 会让人以为下单被拒；判 `filled` 会凭空多出一笔成交。**两者都会让记录说谎。**

幅度按标的区分：默认 ±10%，`588` 前缀（科创板 ETF）±20%，
其余 20% 的标的用 `SC_LIMIT_20_CODES` 显式列出（填裸六位数即可，框架会归一化）。
**框架刻意不内置一份「哪些代码是 20%」的名单** —— 那份名单会随新发基金和规则变化过期，
而且等于把某个人的池子硬编码进框架。

价格按 **0.01 元四舍五入**（`Decimal` + `ROUND_HALF_UP`，不是 Python 的银行家舍入）：
`1.05 × 0.9` 在二进制里是 `0.9449999999999998`，用 float 取整会得到 0.94，
比交易所口径低一分钱 —— 而那一分钱正好决定「能不能卖掉」。

### 持仓快照的保鲜期：默认**关**

「只卖不买」那道闸的前提是「持仓已对账」。原来的判据只有「读得到」——
执行端挂了、持仓文件三天没更新，框架仍判已对账，过期持仓被当成「还在手上」的证据。

`SC_MAX_POSITION_STALE_DAYS`（默认 `0` = 不检查）打开后：快照落后超过 N 个交易日、
或没有时间戳 ⇒ 判未对账 ⇒ 当日只卖不买。

**为什么默认关**：执行端本来就不一定频繁写持仓，打开会误伤正常场景。
这条开关的价值取决于执行端的可靠性 —— 应由使用者按自己的部署决定，
而不是由框架替他选一个可能天天误伤的默认值。

## 六、刻意没做的几件事

| 没做 | 为什么 |
|---|---|
| **第二个 HTTP 投递后端** | 该方案被否决过一次，不在开源版里复活。收益（不再依赖 Gist）不足以抵消「多一个要维护的投递路径」。**也没留空壳接口** —— 一个不能用的类不是扩展点，是噪音；要加只需在**仓库外**写一个 `Transport` 子类，让 `SC_TRANSPORT` 指过去（怎么装见 `ARCHITECTURE.md` 第六节）。★ 注意措辞：**「没有第二个」，不是「没有」** —— 内置的 `GistTransport` 本身走的就是 HTTPS |
| **券商专属的执行端实现** | 每个券商终端的接入方式都不一样，内置一个就等于宣告「只支持这一家」，那家之外的人全都用不上。真正该给的是**接入指南**（见 [`EXECUTOR_GUIDE.md`](EXECUTOR_GUIDE.md)），契约只有三个方法，接谁都可以 |
| **回测引擎** | 本框架和回测框架是**正交**的。把判断写成纯函数 `decide(ctx)`：回测时给 backtrader / qlib 写一层薄适配去调它，实盘时由本框架调**同一个函数**。**策略本体不写两遍 —— 两边各写一次的，是适配层。** 内置一个半吊子回测器，只会让人以为自己有了一个回测器 |
| **产生端去重** | 会引入新的共享状态；当前「同秒同码同向只推一次」的前提在单进程下成立。**已知缺口写进 [`WIRE_CONTRACT.md`](WIRE_CONTRACT.md) 而不是悄悄补上** |
| **读数缓存** | 见第四节 —— 配额换正确性 |
| **统一的 code 后缀** | 见 [`WIRE_CONTRACT.md`](WIRE_CONTRACT.md) 第四节：两套后缀并存是**兼容性要求**，不是历史包袱 |
| **策略里的任何 I/O 便利** | 破坏可回放性。策略要取数只有 `ctx` 一条路，`tests/test_strategy_contract.py` 里有绊线盯着 |

### ★ 为什么执行端给的是「协议」，而不是一个能抄的基类

上一张表里「不内置券商执行端」这一条，有个很自然的反驳：
**那你至少给个能继承的基类吧？**

骨架是给了（[`EXECUTOR_GUIDE.md`](EXECUTOR_GUIDE.md)），但它**不是靠继承来的** ——
`Executor` 是结构化类型（`typing.Protocol`），不是 `abc.ABC`。差别在这里：

- **`Transport` 是 ABC，要求显式继承。** 因为后端是一族要被逐条扫过的实现，
  契约测试拿同一套用例跑遍它们 —— 写错继承关系本身就是错误，该当场拦下。
- **执行端只有「一个内置实现」（`PaperExecutor`），而且它是个占位。** 真实用法是你在旁边写一个类去接
  券商终端，而那个类**通常已经有基类了**（SDK 的适配层、你自己项目里的 `Broker`）。
  要求它再继承一个框架基类，是拿「为了统一而统一」去换一次真实的继承冲突 ——
  而冲突的解法通常是有人开始复制粘贴。

**代价写在明处**：`@runtime_checkable` 的 `isinstance` **只数方法名在不在，
不比对签名**。所以它是顺手的自检，**不是保证**。真正的保证是
`tests/test_executor_contract.py`：一个**不继承任何东西**的最小执行端，
真的被装进链、跑完一轮、它写回去的回执与持仓真的被产生端读到。

## 七、如果只能记一条

**每个「失败时怎么办」都要问一遍「反过来做会怎样」，并把这个判断写进代码旁边。**

本仓库所有 `fail-closed` 的方向都不是从「保守」推出来的，是从
**「哪边错了更疼」** 推出来的。两者的结论在三个闸门里**全都不一样** ——
这正是这条规则值得单独存在的理由：

> 如果「保守」就能得出正确答案，那就不需要判断了。
> 需要判断的地方，恰恰是「保守」会给出错答案的地方。
